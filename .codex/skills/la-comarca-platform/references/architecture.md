# Current and target architecture

## Current state

- Public frontend: static HTML generated by `scripts/build.mjs` and `scripts/pages.mjs`, with progressive enhancement in `public/*.js` and shared CSS in `public/styles.css`.
- Backend: one Cloudflare Worker in `api/worker.mjs`, routing public agenda/materials, registration, CMS, and legacy `/equipo`.
- Operational persistence: Notion data sources for agenda, materials, catechism, transport, and registrations.
- Platform persistence: D1 stores Better Auth users/sessions/rate limits, invitations/grants, and a minimal panel update log; it is not yet the operational domain database.
- Auth: Better Auth email/password sessions for `/cms`; Cloudflare Access JWT validation remains for bootstrap/legacy `/equipo`.
- Deployment: GitHub Actions publishes the static site to GitHub Pages. A separate manual workflow now verifies and can deploy the Worker; it does not deploy automatically.

## Target direction

Keep a modular monolith: edge route handlers, domain/application services, Notion/D1/notification adapters, and a coherent CMS shell. Introduce a first-class application database only when workflows require transactions, private scoping, reliable audit/history, or availability guarantees Notion cannot provide.

Avoid microservices, a second frontend framework, or a broad ORM migration unless a measured constraint requires it.
